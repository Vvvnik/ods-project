= Specification and Statement Generation
:sectnums:

== Purpose

The `SpecificationGenerator` module automatically generates specification and operational documents statement tables based on attributes from .adoc files.

The system automatically:

* Scans all .adoc files in component modules;
* Extracts document attributes (codes, names, parts);
* Creates specification tables (`specification-table.adoc`);
* Creates operational documents statement tables (`statement-table.adoc`);
* Processes approval sheets (ЛУ);
* Integrates with PDF generation process.

=== File Structure

[source,text]
----
components/{name}/modules/{module_name}/
├── pages/
│   ├── Specification.adoc              # ← Specification document
│   ├── Statement_of_Operational_Documents.adoc
│   └── *.adoc                          # ← Other documents
└── partials/tables/
    ├── specification-table.adoc        # ← Automatically generated table
    └── statement-table.adoc             # ← Automatically generated table
----

=== Configuration

The system works only when PDF generation is enabled in config.yml:

[source,yaml]
----
defaults:
  pdf:
    enabled: true                       # ← Must be enabled
    generate_specification: true        # ← Generate specification and statement tables

components:
  - name: information-system
    pdf:
      enabled: true                     # ← For specific component
      generate_specification: true      # ← Can be disabled for specific component
----

To control specification and statement table generation, use the `generate_specification` parameter:

* Default: `true` (generation enabled);
* Can be disabled for specific component by setting `generate_specification: false`;
* Generation runs only if both `enabled: true` and `generate_specification: true` are set.

[NOTE]
====
If you enable PDF generation (`pdf.enabled: true`) but do not use automatic specification and statement table generation, it is recommended to set `generate_specification: false` in the `defaults` section or in specific component settings. This prevents unnecessary table generation and speeds up the build process.
====

:warning-caption: Warning

[WARNING]
When generation is disabled (`generate_specification: false`), existing table files (`specification-table.adoc` and `statement-table.adoc`) are **not automatically deleted**.

If you delete these files manually, specification and statement documents from the `pages` folder that reference these tables via `include` directive will require correction or deletion, otherwise PDF generation will fail due to missing files.

=== Execution Order

Table generation is executed in start.rb before PDF generation (step 4.1):

[source,ruby]
----
# 4.1. Generation of specification and statement tables
# (before PDF generation, so tables are ready for inclusion in documents)
pdf_settings = ConfigParser.get_pdf_settings(comp, cfg)
if pdf_settings[:enabled]
  SpecificationGenerator.generate_for_component(comp, cfg)
end

# 5. PDF generation
PdfGenerator.generate_pdfs(comp, KROKI_URL, cfg)
----

== Generated Tables

=== specification-table.adoc

The specification table contains a list of all module documents with their codes and names.

Table format:

[cols="5,8,3", options="header, breakable"]
|===
^|Designation ^|Name ^|Note

|{nbsp} |{nbsp} |{nbsp}
|===

Example content:

[source,asciidoc]
----
| ABC.0001-01 | Specification |
|             | {name_component} |
| {nbsp} |  |
| ABC.0001-01-ЛУ | Specification |
|                | Approval Sheet |
| {nbsp} |  |
| ABC.0001-01 П3 01 | Description of Automated Functions |
| {nbsp} |  |
| ABC.0001-01 П3 01-ЛУ | Description of Automated Functions |
|                      | Approval Sheet |
----

Features:

* For all documents except the specification itself, full document code (`full_code`) is used;
* For specification document, only the first part of code (`code_contract`) is used;
* Approval sheets (ЛУ) are automatically added with `-ЛУ` suffix;
* Multi-line entries are aligned with spaces by code length;
* Separators `{nbsp}` are added between entries.

=== statement-table.adoc

The operational documents statement table contains a list of documents with number of copies and location.

Table format:

[cols="4,7,1,2", options="header, breakable"]
|===
^|Designation ^|Name ^|Copies ^|Location

|{nbsp} |{nbsp} |{nbsp} |{nbsp}
|===

Example content:

[source,asciidoc]
----
| ABC.0001-01 20 01 | Statement of Operational Documents ^| 1 | {folder_number_contract} |
| ABC.0001-01 13 01 | Program Description ^| 1 | {folder_number_contract} |
| ABC.0001-01 35 01 | Programming Language Description ^| 1 | {folder_number_contract} |
----

Features:

* Specification is automatically excluded from statement;
* Full document code (`full_code`) is used;
* Text part is formed with line breaks (`+`);
* Number of copies is always 1;
* Location is taken from `folder_number` attribute.

== Working with Document Attributes

=== Used Attributes

The system extracts the following attributes from .adoc files:

.Document attributes
[cols="2,3", options="header, breakable"]
|===
^|Attribute ^|Description

|`name_document_master`
|Document name (used to determine document type)

|`name_document_slave`
|Document subtitle (document name 2)

|`name_component`
|Component name (main name)

|`name_document_main`
|Main document name (for specification)

|`code_contract`
|Contract code (extracted from contract.adoc or file)

|`code_document`
|Document code (document number according to GOST)

|`tom`
|Document part/volume number

|`full_code`
|Full document code (template with substitution)

|`folder_number`
|Folder number (for statement)

|`approval-page`
|Presence of approval sheet (true/false)

|===

=== Document Code Resolution

The system automatically resolves nested attributes in `full_code`:

[source,asciidoc]
----
// In document:
:full_code: {code_contract} {code_document} {tom}

// System substitutes values:
// {code_contract} → ABC.0001-01 (from contract.adoc)
// {code_document} → П3 (from file itself)
// {tom} → 01 (from file itself)

// Result: ABC.0001-01 П3 01
----

Resolution logic:

1. `full_code` is extracted from document;
2. Presence of nested attributes `{code_contract}`, `{code_document}`, `{tom}` is checked;
3. `code_contract` is searched in file itself, then in `contract.adoc`;
4. Values are substituted into template;
5. Extra spaces are removed.

=== code_contract Extraction

The system searches for `code_contract` in the following order:

1. In the .adoc file itself;
2. In file `modules/ROOT/partials/contract.adoc`;
3. If not found, empty string is returned.

[source,ruby]
----
def self.extract_code_contract(adoc_file)
  # First check in file itself
  attrs = extract_attributes(adoc_file)
  return attrs['code_contract'] if attrs['code_contract']
  
  # If not, search in contract.adoc
  file_dir = File.dirname(adoc_file)
  contract_path = File.join(file_dir, '../../ROOT/partials/contract.adoc')
  if File.exist?(contract_path)
    contract_attrs = extract_attributes(contract_path)
    return contract_attrs['code_contract'] if contract_attrs['code_contract']
  end
  
  ''
end
----

== Table Generation Logic

=== Document Presence Detection

The system checks for presence of specification and statement documents:

[source,ruby]
----
def self.has_specification_document(adoc_files)
  adoc_files.any? do |adoc_file|
    attrs = extract_attributes(adoc_file)
    name_doc = attrs['name_document_master'] || ''
    filename = File.basename(adoc_file, '.adoc').downcase
    
    name_doc.downcase.include?('спецификация') || 
    name_doc.downcase.include?('specification') ||
    filename.include?('спецификация') ||
    filename.include?('specification')
  end
end
----

Check is performed by:

* `name_document_master` attribute (contains "спецификация" or "specification");
* File name (contains "спецификация" or "specification").

Statement presence is checked similarly.

=== File Sorting

Before processing, files are sorted by priority:

1. Specification (priority 0);
2. Statement (priority 1);
3. Other documents (priority 2).

This ensures correct order of rows in tables.

=== Specification Row Formation

For each document, one or more rows are formed:

[source,ruby]
----
# Main document row
text_elements = [name_doc, tom_phrase, name_prog_main].compact.reject(&:empty?)

# For specification, additional row is added
if is_specification && !name_document_main.to_s.strip.empty?
  # Row with name_document_main is added
end
----

Features:

* For specification, only first part of `full_code` (contract code) is used;
* For other documents, full resolved `full_code` is used;
* Document parts are displayed as "Часть первая", "Часть вторая", etc.;
* Multi-line entries are aligned with spaces.

=== Statement Row Formation

For each document (except specification), one row is formed:

[source,ruby]
----
text_part = [name_doc, tom_phrase, name_prog].compact.reject(&:empty?).join(" +\n")

row = "| #{code_part} | #{text_part} ^| 1 | #{folder_number} |{nbsp}  |  |  |"
----

Features:

* Specification is automatically excluded;
* Text part is formed with line breaks (`+`);
* Number of copies is always 1;
* Location is taken from `folder_number` or default value "Папка №1" is used.

=== Document Part Processing

The system determines whether to show document part:

[source,ruby]
----
excluded_keywords = %w[specification спецификация statement ведомость]
show_part = name_prog != name_prog_main &&
            !tom.to_s.strip.empty? &&
            !excluded_keywords.any? { |w| name_doc.to_s.downcase.include?(w) }
tom_phrase = "Часть #{ordinal_word_ru(tom.to_i)}" if show_part
----

Part is shown if:

* `name_prog` differs from `name_prog_main`;
* `tom` is not empty;
* Document name does not contain excluded keywords.

=== Number to Ordinal Conversion

The system converts numbers to ordinal words in Russian:

[source,ruby]
----
def self.ordinal_word_ru(n)
  units = {
    1 => 'первая', 2 => 'вторая', 3 => 'третья', ...
  }
  # Processing units, tens, hundreds
end
----

Examples:

* 1 → "первая";
* 2 → "вторая";
* 21 → "двадцать первая";
* 30 → "тридцатая".

== Approval Sheet Processing

The system automatically adds approval sheet (ЛУ) entries to the specification table based on the `approval-page` attribute and other document conditions. Approval sheets receive a code with `-ЛУ` suffix (e.g., `ABC.0001-01 П3 01-ЛУ`).

Detailed information about the approval sheet system, generation conditions, and attribute configuration is described in a separate guide: xref:Approval_Sheet_System.adoc[Approval Sheet System].

== Document Integration

=== Including Tables in Documents

Tables are included in documents via `include` directive:

[source,asciidoc]
----
[cols= "5,8,3", options="header, breakable"]
|===
^| Designation ^| Name ^| Note
|                                   ^| {nbsp}  |
|                                   ^| [underline]#*Documentation*#  |
|{nbsp} ||

\include::../partials/tables/specification-table.adoc[]

|===
----

Important:

* Use relative path from current file;
* Tables must be ready before PDF generation;
* Tables are automatically overwritten on each generation.

=== Requirements for Automatic Generation

Automatic generation of specification and statement tables requires documents in the `pages` folder that include these tables via `include` directive.

The system automatically creates tables only if:

* PDF generation is enabled (`pdf.enabled: true`);
* Specification generation is enabled (`pdf.generate_specification: true`);
* Specification or statement documents exist in the module (determined by `name_document_master` attribute or file name).

=== Manual Table Creation

You can create your own specification and statement files that do not use automatic functionality:

* Create table files manually in `partials/tables/` folder;
* Write table content yourself;
* Include them in documents via `include` directive;
* Disable automatic generation for the component (`generate_specification: false`) to prevent your files from being overwritten.

When creating tables manually, they will not be automatically updated when documents in the module change.

== Exception Handling

=== Checks and Validation

The system performs the following checks:

* Existence of `pages/` directory;
* Presence of .adoc files (except `index.adoc`);
* Presence of at least one specification or statement document;
* Existence of table directory (created automatically).

=== Error Handling

When necessary data is missing, the system:

* Outputs warnings to console;
* Skips modules without specification/statement documents;
* Creates empty tables if no documents to process.

=== Old Table Cleanup

Before generation, old tables are deleted:

[source,ruby]
----
File.delete(spec_table_path) if File.exist?(spec_table_path) && has_spec
File.delete(statement_table_path) if File.exist?(statement_table_path) && has_stmt
----

This ensures data freshness in tables.

== Functionality Extension

=== Adding New Table Types

To add new table type:

1. Add document presence check method (e.g., `has_custom_document`);
2. Add table generation method (e.g., `append_to_custom_table`);
3. Add call in `generate_specification`;
4. Update table type determination logic.

=== Changing Table Format

Table format can be changed by modifying row formation methods:

[source,ruby]
----
def self.append_to_specification_table(adoc_file, module_index_path, table_path, is_approval: false)
  # Change row format
  row = "| #{code_part} | #{element} | #{custom_column} |"
  # ...
end
----

:warning-caption: Warning

[WARNING]
When automatically regenerating the system (through `ruby tools/start.rb`), all automatically generated tables will be overwritten. This means any manual changes in `specification-table.adoc` and `statement-table.adoc` files will be lost.

For permanent changes to generation logic, modify source code in `tools/lib/specification_generator.rb`, not the generated files themselves.
