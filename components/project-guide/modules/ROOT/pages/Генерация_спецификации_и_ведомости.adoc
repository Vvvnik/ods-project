= Генерация спецификации и ведомости
:sectnums:

== Назначение

Модуль `SpecificationGenerator` автоматически генерирует таблицы спецификации и ведомости эксплуатационных документов на основе атрибутов из .adoc файлов.

Система автоматически:

* Сканирует все .adoc файлы в модулях компонента;
* Извлекает атрибуты документов (коды, наименования, части);
* Создает таблицы спецификации (`specification-table.adoc`);
* Создает таблицы ведомости эксплуатационных документов (`statement-table.adoc`);
* Обрабатывает листы утверждения (ЛУ);
* Интегрируется с процессом генерации PDF.

components/{name}/modules/{module_name}/

│   ├── Ведомость_эксплуатационных_документов.adoc

=== Конфигурация

Система работает только при включенной генерации PDF в config.yml:

[source,yaml]
----
defaults:
  pdf:
    enabled: true                       # ← Должно быть включено

components:
  - name: information-system
    pdf:
      enabled: true                     # ← Для конкретного компонента
----

=== Порядок выполнения

Генерация таблиц выполняется в start.rb перед генерацией PDF (этап 4.1):

[source,ruby]
----
# 4.1. Генерация таблиц спецификации и ведомости
# (до генерации PDF, чтобы таблицы были готовы для включения в документы)
pdf_settings = ConfigParser.get_pdf_settings(comp, cfg)
if pdf_settings[:enabled]
  SpecificationGenerator.generate_for_component(comp, cfg)
end

# 5. Генерация PDF
PdfGenerator.generate_pdfs(comp, KROKI_URL, cfg)
----

== Генерируемые таблицы

=== specification-table.adoc

Таблица спецификации содержит список всех документов модуля с их кодами и наименованиями.

Формат таблицы:

[cols="5,8,3", options="header, breakable"]
|===
^|Обозначение ^|Наименование ^|Примечание

|{nbsp} |{nbsp} |{nbsp}
|===

Пример содержимого:

[source,asciidoc]
----
| ABC.0001-01 | Спецификация |
|             | {name_component} |
| {nbsp} |  |
| ABC.0001-01-ЛУ | Спецификация |
|                | Лист утверждения |
| {nbsp} |  |
| ABC.0001-01 П3 01 | Описание автоматизируемых функций |
| {nbsp} |  |
| ABC.0001-01 П3 01-ЛУ | Описание автоматизируемых функций |
|                      | Лист утверждения |
----

Особенности:

* Для всех документов, кроме самой спецификации, используется полный код документа (`full_code`);
* Для документа спецификации используется только первая часть кода (`code_contract`);
* Автоматически добавляются листы утверждения (ЛУ) с суффиксом `-ЛУ`;
* Многострочные записи выравниваются пробелами по длине кода;
* Между записями добавляются разделители `{nbsp}`.

=== statement-table.adoc

Таблица ведомости эксплуатационных документов содержит список документов с указанием количества экземпляров и места нахождения.

Формат таблицы:

[cols="4,7,1,2", options="header, breakable"]
|===
^|Обозначение ^|Наименование ^|Кол. экз. ^|Место нахождения

|{nbsp} |{nbsp} |{nbsp} |{nbsp}
|===

Пример содержимого:

[source,asciidoc]
----
| ABC.0001-01 20 01 | Ведомость эксплуатационных документов ^| 1 | {folder_number_contract} |
| ABC.0001-01 13 01 | Описание программы ^| 1 | {folder_number_contract} |
| ABC.0001-01 35 01 | Описание языка программирования ^| 1 | {folder_number_contract} |
----

Особенности:

* Спецификация автоматически исключается из ведомости;
* Используется полный код документа (`full_code`);
* Текстовая часть формируется с переносами строк (`+`);
* Количество экземпляров всегда равно 1;
* Место нахождения берется из атрибута `folder_number`.

== Работа с атрибутами документов

=== Используемые атрибуты

Система извлекает следующие атрибуты из .adoc файлов:

.Основные атрибуты документов
[cols="2,3", options="header, breakable"]
|===
^|Атрибут ^|Описание

|`name_document_master`
|Название документа (используется для определения типа документа)

|`name_document_slave`
|Подзаголовок документа (название документа 2)

|`name_component`
|Название компонента (основное наименование)

|`name_document_main`
|Основное наименование документа (для спецификации)

|`code_contract`
|Код договора (извлекается из contract.adoc или файла)

|`code_document`
|Код документа (номер документа по ГОСТ)

|`tom`
|Номер части/тома документа

|`full_code`
|Полный код документа (шаблон с подстановкой)

|`folder_number`
|Номер папки (для ведомости)

|`approval-page`
|Наличие листа утверждения (true/false)

|===

=== Разрешение кодов документов

Система автоматически разрешает вложенные атрибуты в `full_code`:

[source,asciidoc]
----
// В документе:
:full_code: {code_contract} {code_document} {tom}

// Система подставляет значения:
// {code_contract} → ABC.0001-01 (из contract.adoc)
// {code_document} → П3 (из самого файла)
// {tom} → 01 (из самого файла)

// Результат: ABC.0001-01 П3 01
----

Логика разрешения:

1. Извлекается `full_code` из документа;
2. Проверяется наличие вложенных атрибутов `{code_contract}`, `{code_document}`, `{tom}`;
3. `code_contract` ищется в самом файле, затем в `contract.adoc`;
4. Значения подставляются в шаблон;
5. Лишние пробелы удаляются.

=== Извлечение code_contract

Система ищет `code_contract` в следующем порядке:

1. В самом .adoc файле документа;
2. В файле `modules/ROOT/partials/contract.adoc`;
3. Если не найден, возвращается пустая строка.

[source,ruby]
----
def self.extract_code_contract(adoc_file)
  # Сначала проверяем в самом файле
  attrs = extract_attributes(adoc_file)
  return attrs['code_contract'] if attrs['code_contract']
  
  # Если нет, ищем в contract.adoc
  file_dir = File.dirname(adoc_file)
  contract_path = File.join(file_dir, '../../ROOT/partials/contract.adoc')
  if File.exist?(contract_path)
    contract_attrs = extract_attributes(contract_path)
    return contract_attrs['code_contract'] if contract_attrs['code_contract']
  end
  
  ''
end
----

== Логика генерации таблиц

=== Определение наличия документов

Система проверяет наличие документов спецификации и ведомости:

[source,ruby]
----
def self.has_specification_document(adoc_files)
  adoc_files.any? do |adoc_file|
    attrs = extract_attributes(adoc_file)
    name_doc = attrs['name_document_master'] || ''
    filename = File.basename(adoc_file, '.adoc').downcase
    
    name_doc.downcase.include?('спецификация') || 
    name_doc.downcase.include?('specification') ||
    filename.include?('спецификация') ||
    filename.include?('specification')
  end
end
----

Проверка выполняется по:

* Атрибуту `name_document_master` (содержит "спецификация" или "specification");
* Имени файла (содержит "спецификация" или "specification").

Аналогично проверяется наличие ведомости.

=== Сортировка файлов

Перед обработкой файлы сортируются по приоритету:

1. Спецификация (приоритет 0);
2. Ведомость (приоритет 1);
3. Остальные документы (приоритет 2).

Это обеспечивает правильный порядок строк в таблицах.

=== Формирование строк спецификации

Для каждого документа формируется одна или несколько строк:

[source,ruby]
----
# Основная строка документа
text_elements = [name_doc, tom_phrase, name_prog_main].compact.reject(&:empty?)

# Для спецификации добавляется дополнительная строка
if is_specification && !name_document_main.to_s.strip.empty?
  # Добавляется строка с name_document_main
end
----

Особенности:

* Для спецификации используется только первая часть `full_code` (код договора);
* Для остальных документов используется полный разрешенный `full_code`;
* Части документов отображаются как "Часть первая", "Часть вторая" и т.д.;
* Многострочные записи выравниваются пробелами.

=== Формирование строк ведомости

Для каждого документа (кроме спецификации) формируется одна строка:

[source,ruby]
----
text_part = [name_doc, tom_phrase, name_prog].compact.reject(&:empty?).join(" +\n")

row = "| #{code_part} | #{text_part} ^| 1 | #{folder_number} |{nbsp}  |  |  |"
----

Особенности:

* Спецификация автоматически исключается;
* Текстовая часть формируется с переносами строк (`+`);
* Количество экземпляров всегда равно 1;
* Место нахождения берется из `folder_number` или используется значение по умолчанию "Папка №1".

=== Обработка частей документов

Система определяет, нужно ли показывать часть документа:

[source,ruby]
----
excluded_keywords = %w[specification спецификация statement ведомость]
show_part = name_prog != name_prog_main &&
            !tom.to_s.strip.empty? &&
            !excluded_keywords.any? { |w| name_doc.to_s.downcase.include?(w) }
tom_phrase = "Часть #{ordinal_word_ru(tom.to_i)}" if show_part
----

Часть показывается, если:

* `name_prog` отличается от `name_prog_main`;
* `tom` не пустой;
* Название документа не содержит исключаемых ключевых слов.

=== Преобразование чисел в порядковые числительные

Система преобразует числа в порядковые числительные на русском языке:

[source,ruby]
----
def self.ordinal_word_ru(n)
  units = {
    1 => 'первая', 2 => 'вторая', 3 => 'третья', ...
  }
  # Обработка единиц, десятков, сотен
end
----

Примеры:

* 1 → "первая";
* 2 → "вторая";
* 21 → "двадцать первая";
* 30 → "тридцатая".

== Обработка листов утверждения

=== Условия добавления листа утверждения

Лист утверждения (ЛУ) добавляется в спецификацию, если:

1. Атрибут `approval-page` равен `true`;
2. Атрибут `tom` пустой или равен `'01'`;
3. `code_document` равен `'12'` и `tom` равен `'02'`.

[source,ruby]
----
should_add_approval = false

if attrs['approval-page'] == 'true' || attrs['approval-page'] == true
  should_add_approval = true
elsif attrs['tom'].nil? || attrs['tom'].strip.empty? || attrs['tom'] == '01'
  should_add_approval = true
elsif attrs['code_document'] == '12' && attrs['tom'] == '02'
  should_add_approval = true
end
----

=== Формирование кода листа утверждения

Код листа утверждения формируется добавлением суффикса `-ЛУ` к полному коду документа:

[source,asciidoc]
----
// Для документа с кодом: ABC.0001-01 П3 01
// Лист утверждения получит код: ABC.0001-01 П3 01-ЛУ
----

=== Формат строки листа утверждения

[source,asciidoc]
----
| ABC.0001-01 П3 01-ЛУ | Описание автоматизируемых функций |
|                      | Лист утверждения |
----

Строка содержит:

* Код документа с суффиксом `-ЛУ`;
* Название документа;
* Текст "Лист утверждения" на второй строке.

== Обработка исключений

=== Проверки и валидация

Система выполняет следующие проверки:

* Существование директории `pages/`;
* Наличие .adoc файлов (кроме `index.adoc`);
* Наличие хотя бы одного документа спецификации или ведомости;
* Существование директории для таблиц (создается автоматически).

=== Обработка ошибок

При отсутствии необходимых данных система:

* Выводит предупреждения в консоль;
* Пропускает модули без документов спецификации/ведомости;
* Создает пустые таблицы, если нет документов для обработки.

=== Очистка старых таблиц

Перед генерацией старые таблицы удаляются:

[source,ruby]
----
File.delete(spec_table_path) if File.exist?(spec_table_path) && has_spec
File.delete(statement_table_path) if File.exist?(statement_table_path) && has_stmt
----

Это обеспечивает актуальность данных в таблицах.

== Расширение функциональности

=== Добавление новых типов таблиц

Для добавления нового типа таблиц:

1. Добавить метод проверки наличия документа (например, `has_custom_document`);
2. Добавить метод генерации таблицы (например, `append_to_custom_table`);
3. Добавить вызов в `generate_specification`;
4. Обновить логику определения типа таблицы.

=== Изменение формата таблиц

Формат таблиц можно изменить, модифицируя методы формирования строк:

[source,ruby]
----
def self.append_to_specification_table(adoc_file, module_index_path, table_path, is_approval: false)
  # Изменить формат строки
  row = "| #{code_part} | #{element} | #{custom_column} |"
  # ...
end
----

:warning-caption: Внимание

[WARNING]
При автоматической регенерации системы (через `ruby tools/start.rb`) все автоматически сгенерированные таблицы будут перезаписаны. Это означает, что любые ручные изменения в файлах `specification-table.adoc` и `statement-table.adoc` будут потеряны.

Для постоянных изменений логики генерации нужно модифицировать исходный код в `tools/lib/specification_generator.rb`, а не сами генерируемые файлы.
