# Develop: релиз-ноты (последний блок цепочки)

Задаёт **только** тело под `===`. Синтаксис – в common; **не** делай развёрнутую документацию (несколько абзацев + список) – это другой develop-файл.

## Тело

- После пустой строки под `===` – **один абзац**, **4–6 предложений**. Без пустых строк внутри абзаца. **Без** списков, таблиц, второго `===`.
- `===` – суть изменения; без ID и без «Release Note». Формулировка заголовка и абзаца должна **совпадать по смыслу с названием задачи** в источнике (часто строка `# KEY: …` в начале файла): не подменяй «разработка сервиса» на размытое «улучшение», если из текста следует иное. Кратко перефразировать можно, **тип и предмет работ** сохраняй.

## Содержание

- Кратко **что сделано** для читателя заметки, в логике **официального названия** задачи/эпика. По умолчанию без стека (JPA, Flyway, коды HTTP и т.п.), если неспециалисту не нужно. Цель/сервис эпика – 1–2 короткие фразы в том же абзаце, без копипаста.

## Вступление

- Как в develop «документация», но короче; без лишних клише про релиз.

## Self-check

1. Один абзац, 4–6 предложений; нет `*` и списков.
2. Заголовок и текст **согласованы** с названием задачи из входного файла (не другая тема).
3. Тон – заметка о релизе, не полная документация.
