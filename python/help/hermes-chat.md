# Hermes: работа с chat-сессиями

Кратко: интерактивный `hermes` и SDK пишут лог сессии в JSON `session_<session_id>.json` (обычно каталог `~/.hermes/sessions/`). Файлы в `python/help` могут быть копиями/экспортами для разбора – ориентируйся на `session_id` и путь, который выводит твой инструмент.

## Быстрый старт

- Запустить новый чат:
  - `hermes`
- Разовый вопрос без входа в интерактив:
  - `hermes -c "Твой вопрос"`
- Продолжить конкретную сессию:
  - `hermes --resume <session_id>`
  - пример: `hermes --resume 20260420_144608_06b2cc`

## Где брать `session_id`

- Открой нужный файл `session_*.json`.
- Возьми значение поля `session_id`.
- Обычно имя файла содержит тот же id.

## Что хранится в `session_*.json`

- метаданные сессии: `model`, `base_url`, `platform`, время старта/обновления;
- системный промпт;
- список инструментов;
- история сообщений в `messages`.

## История диалога в SDK (`AIAgent`): `chat()` и `run_conversation`

Важно для скриптов и обёрток над Hermes:

- **`agent.chat(message)`** внутри вызывает `run_conversation(message)` **без** `conversation_history`. Каждый такой вызов начинается с **пустой** цепочки сообщений: модель **не видит** предыдущий пользовательский ввод и ответ в том же процессе.
- **`run_conversation(message, conversation_history=...)`** – правильный способ **наращивать** один диалог: во второй и следующие вызовы передаётся `conversation_history` (как правило, `result["messages"]` с прошлого шага). Тогда и API, и накопленный контекст согласованы.
- Файл `session_*.json` обновляется через `_persist_session` **после каждого** завершённого хода и отражает переданный в сохранение список `messages`. Если каждый ход – «изолированный» `chat()` без истории, в логе оказывается **только последний** обмен (короткий `message_count`), хотя приложение снаружи могло склеить несколько ответов в один артефакт.

**Скрипт ODS** `python/src/services/generate_description_hermes.py`: для нескольких задач (ODS-6, ODS-10, …) в **одном** subprocess используется цепочка **`run_conversation` с передачей истории** между шагами – один `session_id`, один полный лог сессии, общий контекст для следующей задачи.

## Решения по контуру Hermes + ODS (кратко)

- Генерация описаний: скиллы из `python/config.hermes.yaml` → `hermes.skills` подмешиваются в **`ephemeral_system_prompt`** через `build_preloaded_skills_prompt` (отдельно от инструментов).
- Пользовательский текст задачи собирается в `description_hermes.build_user_block` и уходит как очередное user-сообщение в цепочке `run_conversation`.
- **`enabled_toolsets: []`** в конфиге: для пакетного текста **без** инструментов Hermes (нет случайных `browser_vision` и т.п.); убрать ключ – снова все toolsets по умолчанию.
- **`skip_memory` / `skip_context_files`**: управляют подмешиванием памяти Hermes и авто-файлов (SOUL/AGENTS/.cursorrules); на скиллы напрямую не влияют.
- Явный **`resume` CLI-сессии** в скрипт не встраивали: один прогон = своя новая SDK-сессия с накоплением истории **внутри** цикла `run_conversation`.
- Минимальный контекст модели для Hermes Agent (64K): при необходимости – `context_length` в конфиге ODS (патч `load_config` в клиенте) или модель с большим окном.
- Список skills для генерации задаётся в `python/config.hermes.yaml` (`hermes.skills`); подмешиваются в системный промпт SDK. Актуальный набор смотри в репозитории (например `my/asciidoc`, `my/release_notes`).

## Контекст Jira: какие файлы, лимиты в коде

Скрипт `python/src/services/generate_description_hermes.py` не шлёт в модель «всю папку» целиком. Отбор и усечение заданы в `python/src/core/release_containers.py` и `python/src/core/text_cleaning.py`, лимиты – в `python/config.hermes.yaml` (блок `description` и `hermes`).

### Какие файлы попадают в контекст задачи

- Берётся `description.input_dir` (в конфиге обычно `tools/jira` относительно `workspace`).
- Учитываются **только подпапки**, имя которых начинается с `bundle_subdirs_prefix` (например `ODS-`), остальное в `input_dir` для бандлов не сканируется.
- Внутри каждой такой папки **рекурсивно** собираются пути к файлам `*.adoc` и `*.md`.
- **Исключения:** любые файлы под каталогом с сегментом пути `images` (без учёта регистра); файлы с базовым именем `release_notes` или `description`; при совпадении stem у `foo.md` и `foo.adoc` в контекст идёт **один** файл – предпочтение у `.adoc`.
- Остальные расширения (`.txt`, бинарники и т.д.) **не** читаются.

Порядок секций `ODS-6`, `ODS-10`, … задаётся `description.issue_order_file` (список ключей; не упомянутые подпапки дописываются в конце по сортировке).

### Лимиты в конфиге (`python/config.hermes.yaml`)

- `description.max_adoc_text_chars` (часто `32000`): верхняя граница **символов** текста из **одного** исходного файла **после** `extract_text_for_embedding`; хвост обрезается.
- `description.max_context_chars` (часто `96000`): верхняя граница **суммарного** текста контекста по **одной** задаче (эпику) в `description_hermes.generate_sections_hermes` перед отправкой в Hermes; при превышении хвост обрезается, в stderr пишется предупреждение.

Числа можно менять под модель и объём экспортов Jira.

### Что делает `extract_text_for_embedding`

Для каждого выбранного файла: чтение UTF-8, построчная «очистка» разметки (`clean_adoc_line_for_index`: снятие части AsciiDoc/HTML шума), нормализация переводов строк, затем **обрезка** до `max_adoc_text_chars` символов. Поэтому в промпт уходит не обязательно тот же объём, что «в файле на диске».

### Пример объёма (снимок, не константа)

Для папки `tools/jira/ODS-6` на момент замера было **4** файла (`ODS-6.md`, `ODS-7.md`, `ODS-8.md`, `ODS-9.md`). Подсчёт **символов Unicode** в сыром содержимом файлов:

- самый большой файл: `ODS-9.md` – **1752** символа;
- сумма по всем четырём файлам: **6366** символов (**9852** байта в UTF-8).

Цифры со временем меняются вместе с экспортами; актуальный подсчёт удобно делать локальным скриптом по каталогу. Даже при малых сырьевых объёмах итог в промпте проходит обработку и лимиты выше.

## Файлы профиля: `USER.md` и `MEMORY.md`

Каталог по умолчанию (домашняя директория пользователя):

- `~/.hermes/memories/USER.md` – шаблон «о пользователе» (имя, обращение, контекст, предпочтения).
- `~/.hermes/memories/MEMORY.md` – **опциональный** второй слой: факты и заметки, которые **вы сами** правите вручную. Hermes **не создаёт** этот файл и **не дописывает** его сам по ходу чата: если файла нет или он пустой, в контекст из этого пути ничего не подставляется «автоматически».

Hermes **склеивает** текст из **существующих и непустых** фрагментов таких файлов (и при необходимости других markdown в каталоге `~/.hermes/memories/`) в **один непрерывный блок** в системном контексте. Содержимое не подаётся параллельными изолированными каналами: всё последовательно попадает в общий слой «память + профиль».

Практика:

- Раньше имело смысл держать разделение **USER** (профиль) и **MEMORY** (доп. заметки, которые вы сами дописываете); оба пути – `~/.hermes/memories/USER.md` и `~/.hermes/memories/MEMORY.md`.
- Технически можно держать **несколько** markdown-файлов в `~/.hermes/memories/` (два–три и больше), разнося темы по смыслу – тогда проще править куски и не раздувать один монолит.
- Сейчас у нас **всё сведено в один** `~/.hermes/memories/USER.md` – этого достаточно, пока объём не мешает сопровождению; если правила те же, что раньше были разнесены по файлам, **`~/.hermes/memories/MEMORY.md` не должен повторять тот же текст** – иначе склеенный блок получится с дублями.
- Когда профиль разрастётся, имеет смысл **разделить по смыслу** (например: роль и домен в `USER.md`, то, что вы хотите хранить отдельно от профиля, в `MEMORY.md`, либо ещё один `.md` под соглашения) – Hermes всё равно соберёт их вместе; важно не дублировать противоречивые правила в разных файлах.

## Практика работы

- Для длинной задачи держи ее в одной сессии и используй `--resume`.
- Для новой темы лучше заводить новую сессию, чтобы не смешивать контекст.
- Если нужно воспроизвести прошлый ответ, сначала открой соответствующий `session_*.json`, потом продолжай через `--resume`.

## Наблюдение по качеству

Если зайти в уже продолженную сессию с обученным контекстом по AsciiDoc, результат обычно получается лучше: ответы точнее и ближе к нужному формату.

## Протокол работы в одной сессии

Чтобы получать максимально точный результат, работай с Hermes как с пошаговым исполнителем: контекст давай частями, а в конце каждого шага ставь конкретную команду.

1. Сборка артефакта (chunking input)

- Не отправляй сразу весь объем файлов и задач.
- Делай подачу по блокам: сначала один смысловой кусок, потом следующий.
- После каждого блока указывай, что именно нужно сделать с этим блоком.

2. Командный слой

- В каждом сообщении должны быть:
  - входные данные;
  - четкое действие.
- Хороший формат запроса: «Вот файл X. Используя правила из A и B, верни итоговый вариант и выдели риски».

3. Фиксация правил (memory/skills)

- Если в процессе принято новое правило (например, новый стандарт формата), его нужно явно проговорить в чате.
- Тогда Hermes будет применять это правило в текущей сессии и стабильнее держать единый стиль ответов.

Итог: ты управляешь потоком как дирижер – даешь порцию контекста и сразу ставишь точную задачу на следующий шаг.

## Как держать одну сессию в CLI при множестве чанков

Выжимка из практики:

1. Зафиксировать единый рабочий объект в начале

- Сразу обозначай: «Рабочий объект – [файл/модуль/задача]».
- Все последующие куски отправляй как продолжение именно этого объекта.

2. Передавать фрагменты как продолжение, а не как новую тему

- Просто докидывай следующий блок контекста.
- Не нужно каждый раз заново пересобирать всю постановку с нуля.
- Логика: каждый новый чанк = следующий шаг в той же цепочке.

3. Явно фиксировать локальные стандарты сессии

- Если есть правило (например, формат, слой валидации, соглашение по API), проговори его как стандарт текущей работы.
- После фиксации правило должно применяться по умолчанию в дальнейших ответах.

4. Операционный фокус

- Вопрос формулируй не как «мы начинаем новую задачу», а как «какой следующий фрагмент нужен для продолжения».
- Это снижает потери контекста и помогает держать непрерывный flow в одной сессии.
